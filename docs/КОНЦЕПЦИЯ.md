# Концепция анализа данных

Документ описывает **общую модель** разбора чужих таблиц: что считается
данными, какие гипотезы выдвигаются, чем они проверяются, что делать, когда
уверенности нет, и как измерять качество. Он не привязан ни к одному файлу
поставщика: файлы-образцы — это только точки на кривой качества.

---

## 1. Задача в общем виде

**Вход:** произвольный файл-таблица от поставщика (`.xls`, `.xlsx`, `.csv`,
HTML-таблица, многостраничный бланк). Ни структура, ни подписи, ни порядок
колонок заранее не известны; у каждого поставщика своя «форма».

**Выход:** нормализованный список позиций и **отчёт о том, как он получен**:

```
позиция = (штрихкод, артикул, наименование, ед. изм.,
           количество, цена, сумма, ставка НДС, сумма НДС, сумма с НДС)
```

**Ключевое требование:** результат должен быть *проверяемым*. Каждая цифра
либо взята из документа, либо посчитана по формуле, и это видно. Ошибка не
должна проходить молча — вместо этого выставляется флаг «требует проверки».

Это задача **структурного вывода** (structured extraction): мы не «читаем
файл», а строим и проверяем гипотезы о его структуре.

---

## 2. Слои модели

Каждый слой решает одну задачу и передаёт следующему не «сырой файл», а
модель с накопленной уверенностью. Такое разделение позволяет менять один
слой, не ломая остальные, и объяснять любое решение.

| Слой | Вопрос | Модуль | Результат |
|---|---|---|---|
| L0. Нормализация источника | что это за файл? | `readers.py` | `SourceFile` → `Sheet.rows`: матрица значений, `None` = пусто |
| L1. Сегментация | где таблицы? | `layout.find_headers`, `layout.find_transposed_block` | список блоков: строка шапки, сколько строк она занимает |
| L2. Роли колонок | что означает каждая колонка? | `detect.classify_header` + `layout` | роль → колонка, с весом и альтернативами |
| L3. Типизация строк | где данные, а где итоги и подписи? | `detect.total_label`, `is_numbering_row`, `is_furniture` | позиции / итоги / служебные строки |
| L4. Нормализация значений | как читать «1 006,75», «20%», «шт.», EAN? | `textutil.py` | типизированные значения |
| L5. Сборка документа | какие строки — один документ? | `extract.py`, `meta.py` | позиции + реквизиты (поставщик, №, дата) |
| L6. Инварианты | сходится ли арифметика? | `validate.py` | ошибки/предупреждения/расчёты |
| L7. Оценка и объяснение | можно ли доверять? | `analysis.py` | `AnalysisReport`: покрытие, арифметика, доверие, решения |

### L1. Сегментация: где таблица

Таблицей считается участок листа, у которого есть **шапка** — строка, где
опознано ≥4 смысловых колонок, из них ≥2 числовых, и обязательно
«наименование». Строки раздела («I. ТОВАРНЫЙ РАЗДЕЛ») шапкой не считаются.

Дополнительно рассматривается **склейка двух строк** («Сумма» + «без НДС» →
«Сумма без НДС»): она принимается, только если даёт строго больше смысловых
колонок, чем любая из строк по отдельности, и верхняя строка действительно
похожа на шапку (≥3 подписей, нет чисел).

Если шапки в строках нет, проверяется гипотеза **другой ориентации**: ищется
блок, где названия полей стоят в первом столбце, и таблица разворачивается
(L1 ↔ L2 меняются местами).

### L2. Роли колонок: что означает колонка

Роль определяется **по подписи** (словарь синонимов + правила в
`detect.classify_header`) со штрихом качества:

* базовая роль — 3.0;
* «цена без НДС» предпочтительнее «цены с НДС» (+2.0);
* «отпускная», «закупочная», «доставка» — минус 3.0;
* «код» без «артикула» — 1.0 (роль-заготовка).

Подписей мало. Поэтому включается **второй контур — проверка по данным**
(`layout.py`):

1. **Профиль колонки**: доля чисел, целых, кодов из 8–14 цифр, текста, доля
   малых целых (похоже на количество), доля значений 0…100 (похоже на ставку).
2. **Достройка ролей**: колонка без подписи, где ≥80 % значений — 8–14-значные
   коды, становится штрихкодом. Так же может быть найдена и не подписанная
   колонка артикула.
3. **Проверка гипотез арифметикой**: для текущей разметки считается доля
   сошедшихся равенств
   * `количество × цена = сумма` (вес 2),
   * `сумма + НДС = всего` **или** `сумма = всего` (режим «НДС в том числе»),
   * `сумма × ставка = НДС` (для обоих режимов).
   Если доля ниже 0.8, перебираются перестановки ролей по тем же колонкам, и
   принимается та, что сходится лучше минимум на 0.25. Это лечит
   перепутанные подписи («Цена» над суммой) без правил под конкретный файл.

Решение каждой такой починки записывается в `AnalysisDecision` и попадает
в отчёт (`--explain`): видно, что и почему изменилось.

### L3. Типизация строк

Строка относится к одной из категорий: **шапка**, **нумерация** (`1 2 3 4…`),
**итог** (подпись из списка: «Итого», «Сумма НДС», «Всего к оплате»…),
**служебная** (реквизиты, подписи, «прописью»), **данные**. Итоговые строки не
становятся позициями, но участвуют в сверке; служебные пропускаются без
предупреждений, чтобы не создавать шум.

### L4. Нормализация значений

Числа разбираются строго (`1 006,75`, `1.006,75`, `1006.75`), но **никогда**
не выдёргиваются из текста: «Двести рублей 00 копеек» остаётся текстом. Это
сознательный отказ от «умного» поиска чисел — он даёт ложные суммы. Штрихкод
проверяется контрольной цифрой EAN, артикул — по шаблонам `арт.`, `код`,
ведущий ASCII-код.

### L6. Инварианты

Проверяются на каждой позиции и на документе:

1. `количество × цена = сумма` (допуск: цент и 0.5 %);
2. `сумма + НДС = сумма с НДС` (или `сумма = всего` в режиме «в том числе»);
3. `сумма × ставка / 100 = НДС` (или `сумма × ставка / (100+ставка)`);
4. итоги документа = сумма строк (по блокам — «итого по странице»);
5. недостающие значения **достраиваются** и помечаются жёлтым («рассчитано»),
   а не подменяют документ.

Расхождение = ошибка (лист «Проверки»), а не молчаливая правка.

### L7. Оценка и объяснение

Для каждого файла считается:

| Метрика | Как считается | Зачем |
|---|---|---|
| покрытие полей | найдено ролей из 10 | видно, чего в документе нет |
| арифметика | доля сошедшихся проверок L6 | главный признак верной разметки |
| полнота | доля заполненных ключевых полей позиции | сколько посчитано программой |
| доверие | `0.35 + 0.35·покрытие + 0.2·арифметика + 0.1·полнота` | одна цифра «можно ли верить» |

Если сверять нечего (в документе нет колонок «сумма»/«сумма НДС» — например,
в электронной ТТН суммы считаются из количества и цены), арифметика
показывается как «не проверялась» и входит в оценку нейтрально, а не нулём.

Порог: **≥ 0.75 — «высокое»**, 0.5…0.75 — «среднее», ниже — «низкое».
Всё, что ниже порога, помечается «требует проверки» — в окне, в журнале,
в JSON и на листе «Сводка» (столбцы «Качество разбора», «Доверие»,
«Проверить»). Это и есть принцип **abstain**: лучше честно сказать «проверь»,
чем выдать правдоподобную ерунду.

## 3. Как расширять (протокол, а не заплатки)

Правило: **правило = данные, а не код под файл**. Любое изменение проходит
три шага.

1. **Синоним/правило** добавляется в словари `detect.py` (`_NAME_HINTS`,
   `_REJECT`, правила `classify_header`) или в веса `layout.py`.
2. **Корпус**: в `tests/synthetic.py` добавляется раскладка, которая раньше
   ломалась (своя функция `v_*` в `VARIANTS`). Реальные файлы заказчика идут
   отдельно (`tests/conftest.py::KNOWN_FILES`).
3. **Метрики**: `pytest` проверяет по корпусу, что
   * число позиций совпадает,
   * все 10 полей восстановлены,
   * арифметика сходится без ошибок,
   * доверие ≥ 0.75.
   Плюс `--selftest .` на реальных образцах: 301 позиция, 0 ошибок.

Если новое правило ухудшает любую из метрик — правило неверное.

---

## 4. Что считается «общим», а что — частным случаем

Общие механизмы (работают на любом файле):

* поиск шапки в любой строке любого листа;
* роли по синонимам + проверка по данным (профиль колонки, арифметика);
* разворот «боковой» таблицы;
* склейка двухуровневой шапки;
* типы строк, нормализация значений, инварианты, доверие.

Частные случаи (закрываются данными, не кодом):

* новые названия колонок → словарь синонимов;
* новые виды итогов → `_TOTAL_PREFIXES`;
* новые служебные строки → `_FURNITURE_HINTS`;
* новые формы реквизитов → `_NUMBER_LABELS`, `_DATE_LABELS` в `meta.py`.

Ограничения зафиксированы осознанно: суммы прописью не превращаются в числа,
штрихкод не ищется в «Примечании», пароли/PDF-сканы/`.ods` не поддерживаются,
файл без шапки вообще (просто числа) — «требует проверки» вместо догадки.

---

## 5. Как проверить, что концепция работает

```bash
python -m pytest -q                       # корпус раскладок + образцы заказчика
python -m konvektor.cli --selftest . -q    # 301 позиция, 0 ошибок на образцах
python -m konvektor.cli --explain файл.xls # отчёт: роли, арифметика, доверие
```

Корпус раскладок (`tests/synthetic.py`) — 13 вариантов одного и того же
документа: шапка глубоко в листе, переставленные колонки, лишние колонки,
двухуровневая шапка, две таблицы, итоги сверху, синонимы, пустые строки,
колонка штрихкода без подписи, «боковая» таблица с реквизитами и без.

Ожидаемый результат: **во всех вариантах** восстанавливаются одни и те же
3 позиции со всеми 10 полями и арифметика сходится. Это и есть определение
«общего алгоритма» в проверяемой форме.
